# Put the Fries in the Bag

A small, playable Roblox restaurant prototype for up to six players. The current iteration focuses on one loop: **fill a bag with fries, sell the full bag for Cash, and repeat**. Each player chooses a restaurant plot with a basic fryer and bag.

All world geometry and UI are generated by code. No paid assets, plugins, external models, or runtime packages are required.

## AGILE development workflow

Develop in small, reviewable iterations. Prove the basic functionality works before adding more systems.

1. Agree on one small outcome and its acceptance criteria before implementation.
2. Implement only what that iteration needs. Put other ideas in the backlog.
3. Run the relevant automated checks and playtest the change in Roblox Studio.
4. Review the playable result with the project owner and use their feedback to choose the next increment.
5. Keep the game playable after every iteration. Fix core-loop failures before expanding scope.

**Current iteration: UI/UX polish.** The project owner confirmed the core version works on 8 October 2026 and requested this design pass. Players choose a restaurant from six plots around a shared plaza. Polish claiming, signage, action buttons, and the Cash display while keeping the 20-fries / $10 loop unchanged. Do not restore the removed progression systems.

**Definition of done for this iteration:**

- Players enter the central plaza without an assigned restaurant, walk to an available entrance, and press E (or tap the proximity prompt) to claim it.
- Claiming requires a loaded profile, a living nearby character, an unoccupied plot, and no existing claim. One player owns one restaurant per session; leaving frees it.
- Six spacious restaurant plots face a central promenade. Ownership is shown on the building; the title is wall art. Never add floating fryer/equipment name tags, now or in future iterations.
- The world uses smooth, untextured surfaces, bright cartoon colors, rounded plaza bushes, and soft lighting. Check the result in Studio before accepting this visual pass.
- Brown central paths connect to brown restaurant walkways. Every restaurant has a high ceiling with a colored roof trim, and a continuous solid hedge boundary encloses the playing area.
- Packing highlights fries per click (currently +1 fry/click) and changes to Click on hover/focus, with the yield retained below. The internal click-rate limit is not shown to players. Selling shows bag capacity/progress until full, then Sell Bag and its Cash value.
- Cash has a visible card at the middle left, with a coin symbol and grouped amount. On short landscape screens it lifts enough to clear the action buttons. Successful sales update the card and reset the bag without a bottom message.
- Clicking, holding the button, or holding F adds fries at the player's counter.
- After claiming, the basic fryer retains its existing online rate of 0.5 fries per second.
- A bag stops filling at 20 fries.
- An empty or partial bag cannot be sold, including through keyboard or direct remote requests.
- Selling a full bag awards $10 exactly once and resets the bag for the next cycle.
- Players' Cash and bags remain independent; teleport returns each player to their own counter.
- Automated checks pass, Studio desktop/mobile and two-player checks pass, and the project owner reviews the result.

Automated checks alone do not finish the iteration. The new claiming/layout/HUD changes still need Studio playtesting and owner review. **Do not add the next feature until this core loop has been validated and the next increment has been agreed.**

Folding, Upgrades, Delivery, Index, and Inventory have been removed from the running game and source modules. Their connected bonus systems—Tickets, random fry variants, discovery rewards, order rewards, and Lunch Rush—are also outside this iteration. They are possible future backlog items, not a commitment to implement them. There are no placeholder menus or active background rewards for these systems.

**Future visual refinement:** replace the current simple fry and bag symbols with more recognizable fries and bag artwork in an agreed later iteration. Keep the current symbols for now.

**World art direction:** aim for a bright, smooth cartoon feel inspired by Pet Simulator. Use SmoothPlastic for code-built surfaces rather than grainy grass, concrete, brick, wood, or metal textures. Favor clear color blocks, warm brown paths, coral/mint restaurants with cream ceilings, and soft lighting with restrained reflections. Solid perimeter hedges frame the district. Detailed rounded restaurant/fryer models remain a later art iteration. No manual Studio asset creation is needed for this pass.

## Open and play

1. Open **FriesGame.rbxlx** in Roblox Studio using **File > Open from File**.
2. Press **Play**. The restaurant appears when the server starts.
3. Walk to a free restaurant entrance and press **E**, or tap the entrance prompt on touch devices. Claiming puts you at its counter.
4. Hold or tap the gold packing button at the bottom centre. It displays **+1 fry/click** and changes to **CLICK** on hover or selection, with the fries-per-click value shown underneath. Its packing hint stays visible for touch users.
5. The adjacent button shows **fries / capacity** and a progress bar. When full, it turns green and reads **SELL BAG +$10**. Selling requires proximity to your own counter.
6. Use **RETURN TO COUNTER** at the top to return to your claimed restaurant. It is disabled before you claim.

Desktop shortcuts: **E** to claim, **F** to pack, and **R** to sell. E is reserved for proximity claiming so it cannot accidentally sell a bag. Touch users have permanent on-screen buttons. There is no menu, folding shortcut, or equipment selection.

Studio uses explicitly labelled **memory-only test mode** by default. Stopping the test resets this mode's progress. This lets an unpublished place run without DataStore permissions.

## Why the Studio edit view looks empty

The place contains scripts; it builds the restaurant and UI at runtime. An empty edit viewport before pressing Play is expected.

- **src/server/world/WorldBuilder.luau** creates the restaurant.
- **src/server/world/StationBuilder.luau** creates counters, basic fryers, bags, customers, and visible fries.
- **src/client/ui/** creates the permanent controls and Cash display.

We can create elements entirely in code, as this prototype does. Roblox Studio can also be used to author detailed models that scripts later place and control. The current polish pass also uses code-built geometry, wall surfaces, UI cards, and symbols. No manual Studio artwork or external asset uploads are required. More detailed art can be a later, agreed iteration.

If the restaurant is still absent after pressing Play, check Studio's Output window for errors.

## Current scope

- Six player-chosen restaurant plots with identical basic fryers and bags, separate entrances, and a shared central plaza.
- Click/hold input and basic online automatic filling.
- One 20-fries bag at a time, sold for a fixed $10.
- Cash display, fry progress, feedback, and return-to-counter teleport.
- Server-side validation, input rate limits, and bounded Cash.
- Existing profile validation, session locking, retries, autosaves, disconnect saves, and shutdown saves.
- Automated domain, persistence, and wiring tests; a reproducible place builder.

Production starts only after a restaurant is claimed. The basic fryer then keeps filling while online, including away from the counter. Full bags halt production. There is no offline production.

## Saving and publishing

Runtime configuration is in **src/shared/config/Runtime.luau**.

- **StudioUseDataStore = false**: Studio sessions use memory only.
- **StudioUseDataStore = true**: Studio uses **FriesProfiles_TEST_v1**. Use a separately published test experience and enable **Studio Access to API Services** for persistence testing.
- Published servers use **FriesProfiles_v1**, regardless of the Studio test flag.

Store names are unchanged. Existing v1 Cash, lifetime counters, and bag fry counts remain usable. Extra fields from the previous prototype remain inert in stored profiles; they are not sent to the UI or used for gameplay. All players use the same basic equipment, and every full bag sells at the current base price, including previously saved bags with old bonuses. New profiles contain only the core fields.

Profiles save approximately every 45–55 seconds and on exit. A server crash or service outage can lose work since the last successful save. An active lock prevents two servers from editing the same profile. If core progress cannot load safely, the server declines that session rather than replacing it with defaults. After an unclean shutdown, a previous lock may take up to three minutes to expire.

Set the experience's maximum player count to **6** before public release. The server reserves one player space on entry, even before claiming, so every admitted player can choose a plot. Extra players are declined after six admissions. Changing StationCount beyond six also requires a restaurant layout change.

## Source layout

    src/
      shared/
        config/       Core economy, runtime settings, and action vocabulary
        domain/       Packing, basic pricing, and profile schema
        util/         Deep copy and rate limiter
      server/
        Main.server.luau       Composition and player lifecycle
        Network.luau           Remote transport
        services/             Data lifecycle, proximity claiming, station ownership, actions, snapshots
        storage/              Session-locked persistence
        world/                Restaurant and basic station geometry
      client/
        Main.client.luau       UI/input composition and remote subscriptions
        controllers/          Input handling
        ui/                   Permanent HUD and shared widgets
    tests/                    Core-loop, persistence, and wiring tests
    tools/                    Place builder and test runner
    docs/                     Architecture, core rules, and Studio acceptance checks

UI modules display server state and request actions. Domain modules own the game rules; they do not create Instances, send messages, or access DataStores.

## Editing workflow

Choose one workflow for a work session:

**Studio:** edit scripts in Explorer, then save the place. Scripts are under ReplicatedStorage/FriesShared, ServerScriptService/FriesServer, and StarterPlayer/StarterPlayerScripts/FriesClient.

**Source files:** edit src/, run the builder, then reopen the generated place. Studio-only edits are not automatically exported to src/. Rebuilding replaces FriesGame.rbxlx.

The optional **default.project.json** supports Rojo. Rojo is not required.

## Build and automated checks

Python 3.9 or newer, standard library only:

    python tools/build.py

The builder embeds every source file into FriesGame.rbxlx and verifies XML parsing and exact source round-tripping.

Optional Rojo equivalent:

    rojo build default.project.json -o FriesGame.rbxlx

Use the official Luau release tools from https://github.com/luau-lang/luau/releases:

    python tools/test.py --luau PATH_TO_LUAU_EXE --compiler PATH_TO_LUAU_COMPILE_EXE

Optional HUD layout previews (requires Pillow):

    python tools/preview_ui.py --luau PATH_TO_LUAU_EXE

These render the real UI modules using engine doubles and approximate fonts into **artifacts/ui-preview/**. They are layout aids, not Roblox screenshots.

See **VALIDATION.md** for recorded results and **docs/STUDIO_TESTS.md** for the remaining engine checks. Standalone Luau tests do not replace a Roblox Studio playtest.
